
## 3. Session 生命周期全景（M5.1 之后）

```text
                          ┌─────────────────────── 唯一 LogicWorkQueue（一条 deque + 一把 mutex）───────────────────────┐
TCP accept ──────────────▶│ INTERNAL_SESSION_REGISTER       (CServer::HandleAccept 成功分支，Start() 之前)          │
客户端登录帧 ─────────────▶│ EXTERNAL_MESSAGE                (CSession::AsyncReadBody → PostMsgToQue)                  │
LoginHandler 成功 ────────▶│ INTERNAL_SESSION_AUTHENTICATE   (LogicSystem::LoginHandler 尾部)                          │
Meeting 命令 ─────────────▶│ MEETING_COMMAND                 (PostMeetingCommandWork)                                  │
CSession 终止 ────────────▶│ SESSION_DISCONNECTED            (SessionDisconnectBridge，M5 建立)                        │
Close 派生 ───────────────▶│ FINALIZE_CLOSE                  (消费者线程内部入队)                                      │
                          └───────────────────────────────────────────┬───────────────────────────────────────────────┘
                                                                      │ 单消费者（SerializedWorkExecutor）
                                                                      ▼  锁外分发
                                                          LogicWorkDispatcher（MeetingService 的唯一 owner）
```

领域状态机（M3 冻结，M5.1 只驱动它）：

```text
(不存在) --REGISTER--> CONNECTED --AUTHENTICATE(uid>0)--> AUTHENTICATED
                 \                    \
                  \                    \--DISCONNECT--> CLOSING --> CLOSED(tombstone)
                   \--DISCONNECT--------------------------/
   CLOSED --AUTHENTICATE--> 拒绝（不复活）      CLOSED --DISCONNECT--> 幂等 no-op
```

## 4. accept 成功后的注册时机（本步最重要的设计裁决）

### 4.1 为什么不能放在 `CSession` 构造函数

```text
CServer::StartAccept():
    make_shared<CSession>(...)      ← 对象在这里就诞生了
    _acceptor.async_accept(...)     ← accept 可能失败
    ...
CServer::HandleAccept(...):
    if (error) { 打印失败日志 }      ← 这条路径下 CSession 从未被接受
```

若在构造函数登记，accept 失败时领域侧会留下一条**永远不会有断线事件**的孤儿记录
（没有 CLOSED，也没有 fan-out）。M5.1 明确不采用"构造函数注册 + disconnect 补偿"。

### 4.2 实际实现（`CServer::HandleAccept` 成功分支）

```cpp
if (!error) {
        const std::string session_id = new_session->GetSessionId();   // 1. 捕获稳定 SessionId
        {
                std::lock_guard<std::mutex> lock(_mutex);
                _sessions.insert(make_pair(session_id, new_session)); // 2. 加入 _sessions
        }
        if (!LogicSystem::GetInstance()->PostSessionRegisterWork(session_id)) {   // 3. 投递（锁外）
                std::cout << "register work rejected because serialized executor is stopping, session: " << ...;
        }
        new_session->Start();                                         // 4. 最后才装载异步读
}
else { std::cout << "session accept failed, error is " << error.what() << std::endl; }   // 无投递点
```

三处刻意选择：

| 选择 | 理由 |
| --- | --- |
| 投递在 `_mutex` **之外** | 队列锁与 `CServer::_mutex` 绝不嵌套（与 M5 断线通知同一锁纪律） |
| 投递在 `Start()` **之前** | accept 线程与 session 读回调线程是并发的（§2 事实 3）；先 `Start()` 会让第一条 legacy 消息有可能先于 REGISTER 入队 |
| `_sessions.insert` 移到 `Start()` 之前 | 消除"正在读但尚未在册"的窗口；语义不变，只是顺序更严 |

`CServer.h` 未修改（无需新成员/新方法）；`CSession.*` 与 `SessionDisconnectBridge.h` 未修改。

## 5. Login 成功 → AUTHENTICATE work

### 5.1 投递点

`LogicSystem::LoginHandler` 的成功尾部（**紧跟 `session->SetUserId(uid);`**）：

```cpp
        //session绑定用户uid
        session->SetUserId(uid);

        // M5.1：只有走到这里才算 legacy 登录真正成功（token 校验、base info、SetUserId
        // 都已完成），此时才把认证事件交给唯一 FIFO。刻意使用上面已验证成功的局部变量 uid，
        // 而不是 CSession 里未初始化的 _user_uid；所有 early return 的失败路径都不会投递。
        if (!PostSessionAuthenticateWork(session->GetSessionId(), uid)) {
                std::cout << "authentication work rejected because serialized executor is stopping, session: " << ...;
        }
```

### 5.2 失败路径（§19）

`LoginHandler` 的三类 early return（`UidInvalid` / `TokenInvalid` / base info 失败）都在
上述代码**之前**，因此：

```text
REGISTER → CONNECTED → login failed → CONNECTED → DISCONNECT → CLOSED
并且**不会**产生 INTERNAL_SESSION_AUTHENTICATE
```

登录失败也不改变 legacy 协议语义：`Defer` 仍然照常回包，`SetUserId` / `UserMgr` 仍然不被触碰。

### 5.3 uid 来源（§22）

认证身份只来自 `LoginHandler` 中已完成 token 校验的局部变量 `uid`；
**绝不**读取 `CSession::_user_uid`（该成员在 `CSession` 构造时未初始化，本步不修改它）。

### 5.4 enqueue 失败（§11）

`PostSessionAuthenticateWork` 返回 false 只表示"队列已进入停止路径"，M5.1：

```text
不改 legacy 登录协议语义 / 不重试 / 不建立第二条异步路径 / 直接调用 MeetingService（禁止）
→ 只按固定措辞记录： "authentication work rejected because serialized executor is stopping, session: …"
```

`CServer` 侧的 REGISTER 采用同一策略（`"register work rejected because serialized executor is stopping, session: …"`）。

## 6. FIFO ordering：为什么不会被打乱

### 6.1 `REGISTER < 第一条业务消息`

```text
1. 结构保证（生产路径）：CServer 在 Start() **之前**投递 REGISTER。
   Start() 之后该会话才第一次装载 async_read_some，读完成回调才可能把第一条 legacy 消息
   交给 PostMsgToQue。因此"第一条消息入队"在**因果上**晚于"REGISTER 入队"。

2. 并发论证：accept（main io_context 线程）与读回调（AsioIOServicePool 线程）确实可以并发，
   所以顺序**不能**靠"同一个线程里先后调用"来保证 —— 必须靠"读操作尚未装载"这一事实。
   这正是把投递放在 Start() 之前的原因。

3. 队列保证：唯一 LogicWorkQueue 只有 push_back + 单消费者 FIFO 取出，没有 kind 优先级、
   没有第二队列、没有插队。先入队者必先前被取出。

4. seam 可观测证据：`DomainSessionOrdering.RegisterAndAuthenticateAreOrderedBeforeTheSessionsFirstCommand`
   断言 [REGISTER, AUTHENTICATE, 3×EXTERNAL_MESSAGE, MEETING_COMMAND] 这一批次中
   MEETING_COMMAND 的响应为 OK（= 先入队的内部 work 对后入队的一切已经生效），
   且有序事件列表恰为 3 条 legacy 消息 + 1 条 Meeting 命令（未按 kind 重排）；
   对照组（去掉 REGISTER）同一批次必须得到 AUTH_REQUIRED。
```

> 观测边界（如实说明）：`IWorkObservationSink` 只为 `MEETING_COMMAND` / `FINALIZE_CLOSE` /
> `SESSION_DISCONNECTED` 提供 dispatch 记录，`INTERNAL_SESSION_*` 没有独立记录点，因此
> "REGISTER 与第一条 legacy 消息的先后"**不能**在 sink 上直接看到；它由第 1/2/3 条结构证据
> 保证，并由第 4 条的"状态已生效"间接锁定。

### 6.2 `AUTHENTICATE < 之后的命令`

`AUTHENTICATE` 由消费者线程在处理 `EXTERNAL_MESSAGE(LOGIN)` 的过程中投递
（`Enqueue` 期间消费者**不持有**队列锁，M4 §6.2 已证明），因此它落在 FIFO **尾部**：
晚于它之前已排队的一切，早于它之后入队的一切。客户端随后发送的 Meeting 命令自然排在其后。

若出现 §12 描述的交错：

```text
REGISTER   LOGIN   MESSAGE_B   AUTHENTICATE   MEETING_COMMAND
```

则 `MESSAGE_B` 先于 `AUTHENTICATE` 被处理（由真实入队次序决定），而 `MEETING_COMMAND` 仍然后于
两者。M5.1 **不做**任何优先级/插队/第二队列来"强制认证优先"。

### 6.3 `DISCONNECT < 迟到命令`

断线仍走 M5 的 `SessionDisconnectBridge`（一次性、只携带稳定 `SessionId`，投递目标是
`LogicSystem::PostSessionDisconnectedWork` → 同一 FIFO）。因此：

```text
REGISTER → AUTHENTICATE → DISCONNECT → 迟到 MEETING_COMMAND
⇒ 迟到命令看到 CLOSED tombstone → SESSION_STATE_REJECTED（而不是 AUTH_REQUIRED）
```

这条链路由 `DomainSessionLifecycle.ConnectedThenAuthenticatedThenClosedFollowsEnqueueOrder` 锁定。

### 6.4 没有直连领域 mutation

```text
CServer.cpp      只调用 LogicSystem::PostSessionRegisterWork        （grep：无 MeetingService）
LogicSystem.cpp  只调用 _work_executor->PostSession*                （grep：无 meeting_service_）
CSession.*       未修改，仍只经过 M5 桥接
```

## 7. Tombstone retention = Deferred（明确的工程债）

```text
TTL                = NO
LRU                = NO
timer              = NO
background cleanup = NO
retention policy   = Deferred（延续 M3 裁决，M5.1 不实现）
```

不实现的原因（必须记录，避免以后"顺手加个 TTL"）：

> Domain Session 的 CLOSED tombstone 是"迟到 work 仍能得到 `SESSION_STATE_REJECTED`
> 而不是被误报成 `AUTH_REQUIRED`"的**唯一依据**。简单 TTL / LRU 回收**无法证明**：
> 队列里尚未被消费的 stale work，一定能在对应 tombstone 被淘汰之前看到它。要安全回收，
> 必须同时引入 **FIFO work completion 水位 + session generation/epoch + 安全回收判定**
> 这类 queue-aware 机制。因此本阶段只记录债，不发明策略。

由此产生的可接受代价：`MeetingService::sessions_` 随进程内出现过的 Session 单调增长
（每个已关闭 Session 保留一条最小 tombstone）。这属于已知且有意的取舍。
