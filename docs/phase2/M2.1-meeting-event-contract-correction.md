> 前置：M2（`3e566df`，纯 `MeetingAggregate`）

## 1. 背景：M2 交付后复核发现的四处契约缺口

M2 完成了纯 `MeetingAggregate` 状态机，35 个测试全绿。但把 M2 的输出与 Phase 1
已冻结的两份文档逐条对照后，发现 M2 的实现**在四个点上无法表达 Phase 1 要求的事件
语义**。这些不是风格问题，而是"下游（M3 `MeetingService`、M4 gRPC 层、客户端回放）
拿不到判断所需的信息"：

| # | 缺口 | 后果 |
|---|---|---|
| A | `MeetingEvent` 没有"事件后状态"字段 | 消费方只能靠自行推断事件后的稳定态，与 Step 1.4 §23.2 的"事件必须携带 state_after"不符 |
| B | `MeetingEvent` 无法携带 `request_id` | 无法把事件与触发它的外部命令关联，Step 1.4 的 correlation 要求落空 |
| C | `MeetingAggregate` 构造函数是 public，Create 不产出事件 | 创建路径**缺少唯一的 `MeetingCreated`**，`MEETING_CREATED` 事件类型在实现中永远不会被产生 |
| D | `ListParticipantViews()` 返回含 `LEFT` 的历史成员 | "当前成员"与"历史成员存储"被混成一个接口，投影契约含糊 |

## 3. 修正 A — `MeetingEvent::meeting_state_after`

### 3.1 变更

`MeetingTypes.h`：

```cpp
struct MeetingEvent {
    // ... 既有字段 ...

    // 该事件所表达的稳定状态。消费方据此判断"事件之后 Meeting 处于什么状态"，
    // 而不需要自行重放状态机。ParticipantJoined 恒为 ACTIVE；
    // ParticipantLeft 为当前状态（不因成员离会而回退）。
    MeetingState meeting_state_after = MeetingState::CREATED;
};
```

`MeetingAggregate::MakeEvent` 增加形参 `MeetingState meeting_state_after`，并在构造时
`event.meeting_state_after = meeting_state_after;`。

### 3.2 各事件的取值来源

| 事件 | `meeting_state_after` | 说明 |
|---|---|---|
| `MEETING_CREATED` | `CREATED` | 创建后即 `CREATED` |
| `PARTICIPANT_JOINED` | **恒为 `ACTIVE`** | 首个非 Host 加入触发 `CREATED → ACTIVE`；后续加入仍为 `ACTIVE`。不存在 "Host 加入时为 CREATED" 的例外 |
| `PARTICIPANT_LEFT` | `meeting_state_` | mutation **之后**的真实状态。成员离会**不得**使 `ACTIVE` 回退为 `CREATED` |
| `MEETING_CLOSED` | `CLOSED` | M3 使用；M2 不产生 |

关键实现细节：Join 与 Leave 都传入**成员变量** `meeting_state_` 的当前值，而
不是硬编码常量。Join 路径上它之所以恒为 `ACTIVE`，是因为 `meeting_state_` 已在同一
次 mutation 内完成 `CREATED → ACTIVE` 转换；用真实状态而非常量，可以让状态机若被
改坏时直接在事件里暴露出来，而不是被常量掩盖。

## 4. 修正 B — 可选 `request_id` correlation

### 4.1 变更

`MeetingTypes.h`：

```cpp
    // 触发本事件的外部命令 id（correlation id）。
    // 注意：这是**关联标识**，不是幂等键；幂等判定由聚合内部的
    // dedupe_context 承担。内部触发的事件（如断线清理）可以不携带。
    bool has_request_id = false;
    RequestId request_id;
```

### 4.2 为什么是 optional 而不是必填

Phase 1 中并非所有事件都由外部命令触发：例如断线清理导致的 `ParticipantLeft` 由系统
内部产生，没有对应的客户端 `request_id`。因此用 `has_request_id` 存在性标志表达
optional，与既有的 `has_actor_user_id` / `has_participant_user_id` 保持一致风格。

### 4.3 为什么不是幂等键

Phase 1 的幂等语义是**业务维度**的：`Join` 的重复判定看 `(User, Session)` 是否已绑定，
`Leave` 看成员是否已处于 `LEFT`。用 `request_id` 做幂等键会让"同一 session 用不同
request_id 重复 Join"绕过幂等检查。因此 `request_id` 只用于**关联**（把回执/事件与
发起命令对上号），幂等继续由 `dedupe_context` 承担。

### 4.4 接口变化

`Join` / `Leave` 签名增加 `request_id`：

```cpp
JoinResult Join(UserId uid, const SessionId& session_id, const RequestId& request_id,
                const MutationParams& params);
LeaveResult Leave(UserId uid, const RequestId& request_id,
                  const MutationParams& params);
```

`MakeEvent` 的最后一个参数由 `const RequestId&` 改为 `std::string dedupe_context`
（幂等上下文与 correlation 是两个独立概念，不再共用一个形参）。调用点构造形如
`"PARTICIPANT_JOINED:meeting-m2-1:2001"` 的上下文。

**被拒绝与幂等命中的路径不产生事件，因此传入的 `request_id` 不产生任何副作用**——
这一点由 `MeetingAggregateDeterminism.UnusedEventIdHasNoEffectOnRejectedPaths` 覆盖。

## 5. 修正 C — `Create` factory 与私有构造

### 5.1 问题

M2 把构造函数设为 public，于是调用方可以这样创建聚合而不产生任何事件——`MEETING_CREATED`
在实现中**永远不会出现**，而它是 Phase 1 事件序列的起点。

### 5.2 变更

构造函数移入 **private**，唯一公开创建路径是静态 factory：

```cpp
static MeetingAggregate Create(const CreateMeetingParams& params,
                               MeetingEvent& created_event);
```

实现：

```cpp
MeetingAggregate MeetingAggregate::Create(const CreateMeetingParams& params,
                                          MeetingEvent& created_event) {
    MeetingAggregate aggregate(params);
    created_event = aggregate.MakeEvent(
        EventType::MEETING_CREATED, params.event_id, params.created_at,
        /*has_actor=*/true, params.host_user_id,
        /*has_participant=*/false, 0, MeetingState::CREATED, params.request_id,
        std::string("MEETING_CREATED:") + params.meeting_id);
    return aggregate;
}
```

`created_event` 采用**出参**而非放入返回结构体：返回值必须是聚合本身（调用方要立刻持有一个
可用的聚合），而事件是创建过程的副产物。出参让"恰好一个事件"在签名层面就可见。

`MeetingCreated` 的形状：`has_actor_user_id = true`（actor = Host）、
`has_participant_user_id = false`、`meeting_state_after = CREATED`、
`has_request_id = true`（Create 一定由外部命令发起）。

## 6. 修正 D — CURRENT 成员投影

### 6.1 变更

```cpp
// 改为：
std::vector<ParticipantView> ListCurrentParticipantViews() const;   // 只含 ACTIVE
```

原 `ListParticipantViews()` 会返回包含 `LEFT` 的历史成员，与"当前成员"的语义冲突。

### 6.2 语义边界

| 接口 | 返回 |
|---|---|
| `ListCurrentParticipantViews()` | 仅 `ParticipantState::ACTIVE` 的成员 |
| `TryGetParticipantView(uid)` | **任意** uid 的历史身份（含 `LEFT`） |
| `BuildMeetingView().active_participant_count` | 与 CURRENT 列表长度**恒等** |
| `CloseContext::participant_identities` | **全部**历史身份（含 `LEFT`，带 `left_at`） |
| `CloseContext::frozen_active_participant_count` | 冻结边界上的 ACTIVE 数 |

即：**"当前成员"与"历史身份存储"是两个不同的投影**，前者用于在线查询，后者用于
关闭时的审计快照。`MeetingAggregateInvariants.CountEqualsActiveParticipantsAndLeftAreRetained`
断言了 `ActiveParticipantCount() == ListCurrentParticipantViews().size()` 这一不变式。

## 8. 非目标（明确不做）

- **不实现 `FinalizeClose`**：`ENDING → CLOSED` 的发布与 work item 调度属于 M3。
  聚合本身永远不进入 `CLOSED`（`BuildClosedSnapshot` 只是纯函数式的快照构造，
  不改变聚合状态，由 `MeetingAggregateSnapshot.BuildingSnapshotDoesNotMutateAggregateState` 锁定）。
- **不实现 `MeetingService` / registry / `ClosedSnapshotRegistry`**：M3。
- **不实现 `SessionDisconnected` fan-out**：M3。
- **不接 gRPC / protobuf / Redis / MySQL**：ChatServer 可执行文件**依旧不链接**
  `MeetingDomain`；接入在 M4。本次未改动任何 `CMakeLists.txt`。
- **不改 `LogicSystem` / `CSession` / `CServer`**：M2.1 完全在 `meeting/` 与 `tests/` 内。
- **不修 `MysqlDao.cpp:95` 的 `control reaches end of non-void function` 告警**：
  既有问题，与本步无关，保持原样。
- **不实现 Phase 1 规划的全部 57 个场景**：仅覆盖聚合当前职责。
