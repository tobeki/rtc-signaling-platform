## B. 服务端 TCP 发送体系

### B.1 进程与线程拓扑（源码事实）

`ChatServer.cpp` 的启动结构（`[SRC]`，`ChatServer.cpp:250-353`）：

```text
main 线程
  ├── boost::asio::io_context io_context            // accept / signal，主线程 run()
  ├── ChatServiceImpl service                        // gRPC ChatService 实现
  ├── ShutdownCoordinator shutdown                   // M6 关闭协调器
  ├── AsioIOServicePool::GetInstance()               // 2 个 io_context + 2 个线程（默认 size=2）
  ├── RedisMgr::GetInstance()
  ├── grpc::Server (BuildAndStart)                   // gRPC 线程 Wait()
  ├── std::shared_ptr<CServer> tcp_server            // TCP accept
  ├── LogicSystem::GetInstance() + SetMeetingSessionDirectory(tcp_server)
  ├── signal_set（SIGINT/SIGTERM；回调只 io_context.stop()）
  ├── StartGrpcThread()
  └── io_context.run()
```

- `AsioIOServicePool` 构造时创建 `_threads`，每线程运行一个 `io_context`（`AsioIOServicePool.cpp:3-16`）。
- `CServer::StartAccept()` 从 pool 取一个 `io_context` 创建 `CSession`（`CServer.cpp:17-21`）；
  accept 本身在主 `io_context` 上。
- gRPC 的 `ChatServiceImpl` handler 运行在 gRPC 线程（`ChatServiceImpl.cpp:10-119`），其中会直接调用
  `session->Send(...)`（`ChatServiceImpl.cpp:39/83/116`）。
- `LogicSystem` 的 legacy callback 运行在唯一 `SerializedWorkExecutor` 的 worker 线程
  （`LogicWorkDispatcher.h` 的 `WorkerLoop`），其中也有 `session->Send(...)`
  （`LogicSystem.cpp:51/167/197/235/288/332/365/385`）。

⇒ `CSession::_socket` 的访问者至少来自：pool 的读/写完成线程、唯一 worker 线程、gRPC 线程。
这是 B.7 并发分析的依据。

### B.2 TCP 帧格式

当前唯一客户端 TCP 协议是 **4 字节头 + JSON 体**（`[SRC]`）：

| 字段 | 宽度 | 字节序 | 证据 |
| --- | --- | --- | --- |
| `msg_id` | 2B（`short`） | 网络字节序（big-endian） | `MsgNode.cpp:9-16`；`CSession.cpp:148-151` |
| `payload_length` | 2B（`short`） | 网络字节序 | `MsgNode.cpp:15-16`；`CSession.cpp:165-168` |
| payload | `payload_length` 字节 | JSON 文本（legacy IM） | `CSession.cpp:207-212`；客户端 `QJsonDocument::fromJson` |

- 客户端发送：`QDataStream` 设 `BigEndian`，写 `uint16 id` 与 `quint16 len`，再追加 JSON
  （`MyChat_Qt/tcpmgr.cpp:429-450`）。
- 服务端发送：`SendNode` 用 `host_to_network_short` 写头和长度（`MsgNode.cpp:9-17`），
  `CSession::Send` 把 `SendNode` 放入队列，`async_write` 发送（`CSession.cpp:58-90`）。
- 服务端接收：`AsyncReadHead` 读 4 字节头并 `network_to_host_short`，再读 body
  （`CSession.cpp:124-220`）。

### B.3 发送路径与队列

`CSession::Send` 的两个重载（`CSession.cpp:58-90`）行为一致：

```text
持 _send_lock
  send_que_size = _send_que.size()
  if (send_que_size > MAX_SENDQUE) → stdout 打日志，return（丢弃；调用方无感知）
  _send_que.push(SendNode)
  if (send_que_size > 0) return      // 已有在途写，交给 HandleWrite 链继续
  async_write(_socket, front)         // 只有队列空时才发起首写
```

- `L2` 的“进入发送队列”只在此处发生；队列满时消息**不进入队列**，调用方仍得到 `void`。
- `HandleWrite` 成功后 `_send_que.pop()`；若非空，继续对队首 `async_write`（`CSession.cpp:251-263`）。
- `HandleWrite` 失败时打印 stdout 并 `Close()`；**不 pop 剩余队列、不重试、不向调用方回报**
  （`CSession.cpp:265-268`）。
- `Send` 没有返回值，也没有 drop 计数；队列满/写失败的可观测性只有 stdout 文本。

### B.4 会话终止与注册表清理（任务 2.1 逐问回答）

这是本轮最重要的修正区域。必须先区分两条链：

```text
(A) 网络层 TCP registry：CServer::_sessions（shared_ptr<CSession>）
(B) 领域 Session 状态：MeetingService::sessions_ / reverse_index_（SessionId → Binding）
```

**证据（`[SRC]`）**：

- `CSession::Close()`（`CSession.cpp:92-103`）：
  - `_session_mtx` 下 `_socket.close()`、`_b_close = true`；
  - 锁外 `NotifySessionDisconnected()`；
  - **没有** `ClearSession()`。
- `CSession::HandleWrite()`（`CSession.cpp:251-274`）：
  - 成功：pop 队列并继续写；
  - 失败：stdout 日志 + `Close()`；
  - **没有** `ClearSession()`。
- `CSession::NotifySessionDisconnected()`（`CSession.cpp:105-118`）：
  - `SessionDisconnectBridge::NotifyDisconnected()`；
  - 只投递稳定 `SessionId`；不持有 `CSession`/socket；不直接调用 MeetingService。
- `SessionDisconnectBridge::NotifyDisconnected()`（`SessionDisconnectBridge.h`）：
  - 锁内把 `posted_` 置位，锁外调用 `ISessionDisconnectSink::PostSessionDisconnectedWork`；
  - 保证同一个会话最多投递一次；队列停止时返回 `REJECTED`，不重试。
- `LogicSystem::PostSessionDisconnectedWork()`（`LogicSystem.cpp:540-543`）：
  - `EnsureWorkQueueStarted()` + `_work_executor->PostSessionDisconnected(session_id)`；
  - 只入唯一 FIFO。
- `LogicWorkDispatcher::SessionDisconnected()`（`LogicWorkDispatcher.cpp:240-247`）：
  - 调用 `meeting_service_.SessionDisconnected(session_id)`；
  - 只做领域处理；**不触碰** `CServer::_sessions`，不调用 `UserMgr::RmvUserSession`。
- `MeetingService::SessionDisconnected()`（`MeetingService.cpp:965-1035`）：
  - 领域 Session `CONNECTED/AUTHENTICATED → CLOSING → CLOSED`；
  - 遍历 `reverse_index_`，对受影响 Meeting 执行 `DisconnectSession`；
  - **不清理** `CServer::_sessions`，也不清 `UserMgr`。
- `CServer::ClearSession()`（`CServer.cpp:58-71`）：
  - `_sessions.find`（**未持 `_mutex`**）；
  - 命中则 `_sessions[session_id]->GetUserId()`（**未持锁**）→ `UserMgr::RmvUserSession(uid)`；
  - 然后持 `_mutex` `_sessions.erase(session_id)`。
- `CServer::FindSessionBySessionId()`（`CServer.cpp:88-101`）：
  - 持 `_mutex` `find` + 复制 `shared_ptr`；未命中返回空。

**逐问回答：**

| # | 问题 | 结论 | 说明 |
| --- | --- | --- | --- |
| 1 | `HandleWrite` 写失败后是否调用 `ClearSession`？ | **否** | 只调用 `Close()`（`CSession.cpp:265-268`）；`Close()` 也不调用 `ClearSession` |
| 2 | `Close()` 是否只向 LogicSystem 投递断线事件？ | **在清理责任上是的** | `Close()` 关闭 socket、置 `_b_close`，并 `NotifySessionDisconnected()`；它不清理 registry，也不清 UserMgr（`CSession.cpp:92-118`） |
| 3 | `SESSION_DISCONNECTED` 的领域处理是否等价于 `CServer` 注册表清理？ | **不等价** | 领域只把 Meeting Session 置 CLOSED 并清 Binding refs；`CServer::_sessions` 与 `UserMgr` 不在该路径（`LogicWorkDispatcher.cpp:240-247`；`MeetingService.cpp:965-1035`） |

**额外边界（不得忽略）：**

- `CServer::ClearSession` 的 `find` / `operator[]` 前段**未持锁**（R-2）；若与 `HandleAccept` 的 insert
  或另一线程的 erase 并发，`clearSession` 可能插入一个空 value 或读到已失效状态；`operator[]`
  后接 `->GetUserId()` 存在空指针解引用风险（源码风险，未构造运行期复现）。
- `ClearSession` 本身不投递领域断线事件；当前所有调用点都在 `Close()` 或 `NotifySessionDisconnected()`
  之后（`CSession.cpp:130-131/139-140/160-161/174-175/194-195/202-203`），因此领域事件当前不会漏；
  但这是调用方纪律，不是 `ClearSession` 的接口契约。
- **不能**用“在 `HandleWrite` 里补一句 `ClearSession`”作为完整修复：它绕不开 B.5 的未初始化
  `_user_uid`、`ClearSession` 的锁问题、领域/注册表两条链的幂等与顺序问题。

### B.5 `ClearSession` 与未初始化 `_user_uid`（任务 2.2）

**源码事实（`[SRC]`）：**

- `CSession.h:67`：`int _user_uid;`（无默认初始化）。
- 构造函数初始化列表（`CSession.cpp:10-11`）只初始化 `_socket`、`_server`、`_b_close`、`_b_head_parse`；
  **没有 `_user_uid`**。
- `SetUserId()`（`CSession.cpp:33-35`）是唯一写点；调用点只有 `LogicSystem::LoginHandler`
  成功路径（`LogicSystem.cpp:133`）。token 校验失败、base info 失败等 early return 都不会设置它
  （`LogicSystem.cpp:59-66/74-77`）。
- `GetUserId()`（`CSession.cpp:36-38`）直接返回 `_user_uid`。
- `CServer::ClearSession()`（`CServer.cpp:60-65`）在 `find` 命中时**无条件**读取 `GetUserId()` 并调用
  `UserMgr::RmvUserSession(uid)`。
- `UserMgr::RmvUserSession()`（`UserMgr.cpp:27-38`）只做 `_uid_to_session.erase(uid)`；不校验 uid、
  不区分“未登录”。

**结论：会。** 一个尚未登录（或登录失败）的 Session 进入 `ClearSession` 时，当前代码会读取
未初始化的 `_user_uid`：

1. 这是读取未初始化 `int` 的未定义行为风险（lvalue-to-rvalue）；值不确定。
2. 不确定的 uid 被传给 `RmvUserSession`，可能**误删另一个真实用户**的 `UserMgr` 映射
   （例如该进程内恰好存在相同 uid 的登录 Session）。
3. 即使不崩溃，也会造成 UserMgr 状态与真实 Session 不一致。

这与 B4/B6 的生命周期风险直接相关，应作为 Phase 3 的前置修复项；但**不能**用“只在 HandleWrite
调用 ClearSession”解决，也不能用“给 `_user_uid` 加个默认值”当作唯一修复而不处理
`ClearSession` 的锁与幂等语义。

### B.6 发送队列上限的精确边界（任务 2.3）

`MAX_SENDQUE` 为 **1000**（`const.h:44`），判断是 `send_que_size > MAX_SENDQUE`
（`CSession.cpp:61/78`），不是 `>=`。

| 进入 `Send` 时队列长度 | 判断 | 动作 | 结束后队列长度 |
| --- | --- | --- | --- |
| 999 | `999 > 1000` 为假 | push | **1000** |
| 1000 | `1000 > 1000` 为假 | push | **1001** |
| 1001 | `1001 > 1000` 为真 | 打印“fulled”、直接 return | 1001（不 push） |

因此：

- **实际允许的最大队列长度是 1001**（不是 1000）。
- 第 1002 条消息在进入时若队列已为 1001，会被丢弃；丢弃**没有返回值、没有计数器、没有回调**。
- 队列满日志打印的是常量 `MAX_SENDQUE`（1000），不是实际长度 1001，容易误读。
- `Send` 的 payload 长度参数是 `short`（`SendNode` 构造 `short max_len`，`MsgNode.h:43`；
  `CSession.cpp:66` 把 `msg.length()` 传入），发送侧**没有** `MAX_LENGTH` 校验；超长 payload
  存在窄化/长度头错误风险（源码推断，未复现）。

### B.7 Socket 并发访问（任务 2.4）

**锁与访问点：**

- `Send`：持 `_send_lock`，读写 `_send_que`，并**发起** `async_write`（`CSession.cpp:58-90`）。
- `HandleWrite`：持 `_send_lock`，pop 队列并继续发起 `async_write`（`CSession.cpp:251-263`）；
  失败时 `Close()`（`:265-268`）。
- `Close`：持 `_session_mtx`，执行 `_socket.close()`、`_b_close = true`（`CSession.cpp:92-98`）。
- `AsyncReadHead` / `AsyncReadBody` / `asyncReadLen`：直接调用 `_socket.async_read_some`，
  **不持 `_send_lock`，也不持 `_session_mtx`**（`CSession.cpp:124-220`）。

**调用线程：**

- 读/写完成 handler 在 `CSession` 所属 pool 的 `io_context` 线程上执行；
- `Send` 可能来自唯一 worker（legacy callback）或 gRPC 线程（`ChatServiceImpl.cpp:39/83/116`）；
- `Close` 当前只由读/写 handler 内部调用（`CSession.cpp:130/139/194/202/267`），没有外部
  `session->Close()` 调用点（全仓 grep；不排除未来新增）。

**判断：**

- 不存在一个覆盖“读发起 / 写发起 / close”的**统一串行化边界**；`_send_lock` 与 `_session_mtx`
  是两把互不覆盖的锁。
- 同一 `boost::asio::ip::tcp::socket` 对象可能被不同执行上下文同时使用：例如 worker/gRPC 线程
  在 `Send` 中发起 `async_write`，pool 线程在 `Close` 中 `_socket.close()`，或 pool 线程正在
  发起 `async_read_some`。
- 这**至少**是并发访问风险，并违反 Boost.Asio 对共享 socket 对象线程安全约束的使用预期；
  **不应**在没有充分证据时直接称为 C++ 语言层面的 undefined behavior。
- 正确方向是：为每个 `CSession` 引入 `strand`（或等价地把所有 socket 操作 post 到同一执行器/
  单线程串行边界），并让 `Send`/`Close`/read 共用一个关闭状态机；`Send` 还应捕获同步
  `async_write` 异常并向上返回可观测结果。
- 现有 `_b_close` 只被写、从未被读（`grep _b_close`：`CSession.cpp:96` 写、`CSession.h:70` 声明；
  没有读取），因此它**不是**有效的“只关闭一次/拒绝新写”闸门。

### B.8 L2–L5 交付层次（任务 2.5）

统一定义：

| 层级 | 定义 |
| --- | --- |
| L2 | 消息进入 Session 发送队列 |
| L3 | 异步写操作成功完成 |
| L4 | 异步写失败可被程序识别 |
| L5 | 客户端实际收到并处理消息 |

现状：

| 层级 | 路径可达？ | 程序可观测？ | 自动化测试可验证？ | 生产可保证？ | 证据 |
| --- | --- | --- | --- | --- | --- |
| L2（legacy / gRPC 通知） | **是** | 仅间接：无返回值；队列满 stdout 文本 | 否（无队列满/丢弃断言） | 否（队列满静默丢弃） | `CSession.cpp:58-90` |
| L2（M6 Meeting 出站） | **否** | 否 | 否 | 否 | `CountingNoWireCollector` 只计数 |
| L3 | 是（legacy） | **否**：成功路径无日志/计数；只能靠“没有错误”推断 | 否 | 否（OS/Asio 层面） | `CSession.cpp:251-263` |

**必须区分：**

- 当前 M6 的 Meeting 出站对象在 L2 都尚未到达（collector 只计数）。

## C. 现有协议体系

### C.1 客户端 TCP 与 gRPC 是两条链路

- 客户端（MyChat_Qt）使用 **TCP + 4B 头 + JSON**（B.2）。
- `message.proto` 定义的是 **服务端之间的 gRPC**（`VarifyService`、`StatusService`、
  `ChatService`），不是客户端 TCP 协议，也不包含 Meeting 消息（`message.proto` 全文）。
- gRPC `ChatService` 的 `NotifyAddFriend/NotifyAuthFriend/NotifyTextChatMsg` 由其他服务调用，
  handler 通过 `UserMgr::GetSession(touid)` 找到本节点 Session，再 `session->Send(...)`
  （`ChatServiceImpl.cpp:10-119`）。
- Meeting 领域是 **transport-neutral** 的，不经过 `message.proto`，也不经过 gRPC。

### C.2 消息 ID 的当前实现限制（任务 2.7）

`CSession::AsyncReadHead()`（`CSession.cpp:148-177`）：

```cpp
short msg_id = 0;
memcpy(&msg_id, ...);
msg_id = network_to_host_short(msg_id);
if (msg_id > MAX_LENGTH) {        // MAX_LENGTH = 2048
    NotifySessionDisconnected();
    _server->ClearSession(_session_id);
    return;
}
short msg_len = 0;
...
if (msg_len > MAX_LENGTH) { ... }
```

必须明确以下区分：

1. **`MAX_LENGTH=2048` 是当前实现的缓冲区/长度限制**，不是 Phase 1 协议规范，也不是
   “合法 Message ID 集合”的定义。Phase 1 §3.1 明确把“message ID 数值”留给 Phase 3
   （`docs/phase1/STEP-1.4-api-contract.md:46-59`）。
2. 判据是 `>` 不是 `>=`：`msg_id == 2048` 当前**通过**，`2049` 才被拒。
3. `msg_id`/`msg_len` 是 **signed short**：负值不会被上述判断拒绝。负 `msg_id` 会继续进入
   `RecvNode`；负 `msg_len` 会继续进入 `RecvNode`/`AsyncReadBody`，其中 `short` 转 `size_t`
   可能形成巨大长度或非法缓冲区运算（源码推断，未运行复现）。
4. 因此 Phase 3 不应把 `2048` 直接写进协议规范；应定义：
   - 显式的合法 ID 集合/范围（与 legacy 1005–1024 及新 Meeting ID 共存）；
   - 合法 payload 长度上界与最小长度校验；
   - 有符号/无符号的明确 wire 语义；
   - 对非法 ID/长度的统一错误处理（不是直接进入业务 handler）。
5. **兼容性**：在修复上述校验前，新 Meeting ID 若大于 2048 会被当前接收端拒绝；若为负值会
   绕过检查；因此新 ID 的选择必须考虑当前接收端行为，或在同一协议版本内先修复校验。

## D. Qt 客户端接收体系

### D.1 接收循环（源码事实）

`MyChat_Qt/tcpmgr.cpp:19-58`：

```text
readyRead:
  _buffer.append(socket.readAll())
  QDataStream stream(&_buffer, ReadOnly);   // 整个 readyRead 只构造一次
  stream.setVersion(Qt_5_0)
  forever:
    if !_b_recv_pending:
      if _buffer.size() < 4: return
      stream >> _message_id >> _message_len
      _buffer = _buffer.mid(4)               // 原地替换 _buffer
    if _buffer.size() < _message_len:
      _b_recv_pending = true; return
    _b_recv_pending = false
    body = _buffer.mid(0, _message_len)
    _buffer = _buffer.mid(_message_len)
    handleMsg(_message_id, _message_len, body)
```

### D.2 发送格式

`uint16 id`、`quint16 len`，再追加 JSON；与服务端 `SendNode` 的网络字节序一致。
客户端只发送 legacy 请求（登录、搜索、好友、聊天），没有 Meeting 命令。

### D.3 多帧解析问题（任务 2.10）

**标记：`SOURCE-BASED HYPOTHESIS — NOT YET REPRODUCED`（基于源码的假设，尚未复现）**

可疑点：

1. `QDataStream stream(&_buffer, ...)` 在 `readyRead` 开始时构造**一次**（`tcpmgr.cpp:24`）；
2. 解析第一个头后，`_buffer = _buffer.mid(4)`（`:39`）替换了 `QByteArray` 对象内容；
3. 随后 `_buffer = _buffer.mid(_message_len)`（`:56`）再次替换；
4. `stream` 的读位置仍停留在第一个头之后的偏移（前 4 字节已被逻辑移除），但下一次
   `stream >> _message_id >> _message_len`（`:36`）仍使用该 stream，读位置没有按新 buffer 重置。

因此，**当一次 `readyRead` 中同时包含两个完整帧时**，第二个帧的头部很可能从错误的偏移读取
（读到第一个 body 的中间或错位数据），导致 `_message_id`/`_message_len` 错误、消息被丢弃或
被错误分发。Qt 文档说明 `QDataStream(QByteArray*)` 不复制数组，数组中数据被替换时流的状态
不再可靠；这是本假设的源码依据。

**不是已复现结论**：未构造“一次 readyRead 两个完整帧”的运行期测试，也未检查 Qt 具体版本下
`QDataStream` 的内部指针语义；因此只能标记为 `[SRC-HYP]`，不能写成已确认缺陷。

### D.4 最小验证方案（本轮不改客户端）

在不修改客户端代码的前提下，用最小实验验证：

1. 用本地假服务器/回环 socket（或现有测试替身）在一次 TCP 写中发送**两个完整帧**，
   例如 `[hdr1][body1][hdr2][body2]`，两个 body 使用不同可识别的 JSON/ID；
2. 让客户端只触发**一次** `readyRead`（合并写、避免中间 flush）；
3. 观察 `qDebug` 的 “Message ID/Length” 与两个 handler 的副作用/信号：
   - 期望：两个 ID 各出现一次，两个 handler 各被调用一次；

  QUERY/LIST_PARTICIPANTS` 的 JSON 解析、`MeetingRequestContext` 构造、`PostMeetingCommandWork`
  调用。
- 因此 Meeting 领域在生产 TCP 上**完全不可达**；M6 adapter 的六 Response 也不会被触发。

### E.3 缺口二：没有 Meeting Egress

- `CountingNoWireCollector` 是唯一生产 collector；它只计数（`CountingNoWireCollector.cpp:14-29`）。
- adapter 不 include `CSession.h`，不调用 `Send`（`MeetingResponseNotificationAdapter.cpp:13-16`）；

- 没有把 `MeetingResponseMessage`/`MeetingNotificationMessage` 映射为 msg_id + JSON/wire 的
  transformer；没有按 `response_target_session_id` / `notification_target_session_id` 找
  `CSession` 并发送的 production egress。
- 因此 M6 的 Meeting 出站在 **L2 之前**就停止（collector 计数），L2/L3/L4/L5 均未到达。

### E.4 缺口三：target session 与 registry 清理不一致

- M6 adapter 用 `IMeetingSessionDirectory::FindSessionBySessionId()` 判活
  （`MeetingResponseNotificationAdapter.cpp:219-244`），CServer 的实现只在 `_sessions` 中查找
  （`CServer.cpp:88-101`）。
- 若 `HandleWrite` 失败后 `_sessions` 未及时清理（B.4），adapter 会把已关闭 socket 的 Session
  判为 “resolved”；Phase 3 egress 若直接 `Send` 会失败/无 L4 反馈。
- 因此 Egress 的前置条件是会话终止/注册表清理语义明确（G.4）。

### E.5 缺口四：没有协议契约

- Meeting 的 wire 字段、msg_id、error response 的 Meeting ID、notification 的关联字段、
  request_id 与 wire correlation 的关系，均未定义；Phase 1 §3.1 明确留给 Phase 3。
- 当前 `MeetingResponseMessage` 没有独立 `meeting_id` 字段（M6 §10.3 已更正）；错误响应若要
  携带 Meeting ID，需要架构裁决，不能由 adapter 私自补字段。

## G. Phase 3 推荐任务拆分

原则：**唯一 FIFO、唯一消费者、single-writer** 不变；不创建第二个业务队列/worker。

### G.1 P3.1 — 协议与生命周期架构裁决（前置）

必须先把以下事项写成设计文档并获批准：

1. Protocol V2 的帧格式/版本/兼容策略；
2. 合法 msg_id 集合（legacy + Meeting）；
3. Meeting 命令/响应/通知的 payload schema；
4. request_id 与 wire correlation 的关系；
5. error response 是否携带 Meeting ID（若需要，修改 typed 消息契约）；
6. Notification 的 best-effort 语义（继承 Phase 1 无 ACK）；
7. 会话终止/清理状态机（B.4/B.5）与 socket 串行化模型（strand）；
8. Windows 构建门禁与 R6 是否纳入本阶段。

### G.2 P3.2 — 服务端 Meeting Command Ingress Adapter

新增独立组件（不得再让 `PostMeetingCommandWork` 无调用者）：

```text
TCP 4B header + JSON body (new Meeting msg_id)
   ↓
解析 command / meeting_id / 可选业务字段
   ↓
服务端认证 Session → authenticated_user_id / session_id / local_server_id
   ↓
MeetingRequestContextBuilder.Build(...)   // 只使用服务端可信值
   ↓
LogicSystem::PostMeetingCommandWork(context, kind, meeting_id)
   ↓
现有唯一 LogicWorkDispatcher FIFO（MEETING_COMMAND）
```

要求：

- 客户端 payload **不得**提供/覆盖 identity 字段；
- `request_id` 可为 adapter 内部生成（Phase 1 §5/§7.5）；
- 非法 command/meeting_id/长度返回协议错误，不进入领域；
- 不创建第二个队列、不直接调用 MeetingService；
- 错误响应是否可编码 Meeting ID 由 P3.1 裁决。

### G.3 P3.3 — 服务端 Meeting Egress（Response / Notification）

```text
MeetingResponseNotificationAdapter
   ↓ typed MeetingOutboundMessage
新 WireCollector（替换 CountingNoWireCollector 的生产实例）
   ↓ msg_id + JSON/wire 编码
按 response_target_session_id / notification_target_session_id
   ↓ IMeetingSessionDirectory 判活
CSession::Send(...)（或新的可观测 Send API）
```

要求：

- 与 P3.2 共用唯一 FIFO/唯一消费者上下文；
- 通知逐目标发送；目标消失则跳过（Phase 1 §21.4）；
- 发送失败不回滚领域；返回可观测的 L4 状态（由 P3.1 决定形式）；
- 不把 `Collect()` 变成第二个队列；
- 不在 adapter 内直接 `Send`（依赖方向不变）。

### G.4 P3.4 — 会话终止与注册表清理硬化（Egress 前置）

必须作为一个独立任务，而不是在 `HandleWrite` 里补 `ClearSession`：

1. `_user_uid` 初始化或显式 `has_user` 状态；`ClearSession` 只在已认证时移除 UserMgr；
2. `ClearSession` 的 `find`/`erase`/`GetUserId` 统一加锁（修复 R-2 的这段）；
3. 统一终止状态机：`Close` / read error / write error / invalid header → 一次且仅一次
   清理（registry + domain + UserMgr），明确谁负责 `ClearSession`；
4. 明确 `CSession::_b_close` 的语义（当前只写不读，应成为拒绝新写的闸门）；
5. 为 socket 操作引入 `strand`/统一执行器，处理 close 与读写的竞争；
6. 明确 `FindSessionBySessionId` 对“正在关闭/已关闭”Session 的返回语义。

### G.5 P3.5 — Qt 客户端解析与 Meeting 接收

1. 先按 D.4 做多帧最小复现；
2. 修复 `QDataStream` 与 `_buffer` 替换的生命周期问题（每帧重建流/显式偏移/先取头再解析）；
3. 增加 Meeting Response/Notification 的 msg_id 与 JSON 处理；
4. response 与 request 的 correlation（按 P3.1 裁决）；
5. 不改变 legacy 消息的既有行为（除非协议版本化）。

### G.6 P3.6 — Windows 工程与构建门禁

1. 把 M4/M5/M6 的 TU 加入 `ChatServer.vcxproj`（及 `ClInclude`）；
2. 在 Windows `Debug|x64` 实际构建并保留日志；
3. 在此之前，所有 Windows 结论保持 `[NOT VERIFIED]`；
4. 不把 Linux 构建成功推断为 Windows 成功。

### G.7 P3.7 — 测试与可观测性

1. **L2**：队列满/丢弃策略测试；`Send` 结果可观测（若 API 改变）；
2. **L3/L4**：写失败的可注入测试（关闭 socket / 对端拒绝），断言返回/回调/计数，
   而不是只看 stdout；
3. **L5**：仅在客户端 ACK/展示测试存在时声明；否则保持 `[NOT VERIFIED]`；
4. 会话清理：未登录 Session → `ClearSession` 不误删 UserMgr；并发 find/erase；
5. socket 串行化：并发 Send/Close 压测（有限、可重复）；
