## 1. Executive Summary

### 1.1 结论

本设计推荐把 Protocol V2 定义为“**沿用既有 4-byte TCP frame、增加严格帧校验、共享 Message ID 注册表和 Meeting V2 JSON schema 的协议 profile**”，而不是替换 TCP frame header：

```text
2B unsigned message_id (network byte order)
2B unsigned payload_length (network byte order)
N bytes UTF-8 JSON payload
```

**RECOMMENDED — PENDING HUMAN APPROVAL**：

1. 保留 4-byte frame，避免 legacy IM、ChatServer 和 Qt 同时迁移到新 header；不引入 magic、版本协商或双 parser。
2. 线上字段统一为 `std::uint16_t` / `quint16`；header 先解析到无符号定宽值，完成合法 ID 和长度验证后才能分配 payload、创建 `RecvNode` 或启动 body read。
3. 单帧 payload 协议上限推荐为 `65,535` bytes；接收实现使用“固定 4B header + 校验后按长度分配的有界 payload buffer”，不再把 `MAX_LENGTH=2048` 同时当接收缓冲、payload 上限和 Message ID 上限。
4. Meeting Message ID 推荐使用 `2001–2008`：六个 request ID、一个通用 response ID、一个通用 notification ID；建立 C++11-compatible、无第三方依赖的共享协议 header，不引入代码生成器。
5. Qt 可提供可选 `request_id`；推荐 Qt 对每个 Meeting 请求生成 UUID。服务端缺失时生成 UUID 并回显。它只用于 correlation，绝不去重 Create；`event_id` 仍是 Event 自身身份。
6. 新建 Meeting Command Ingress Adapter，只做 message ID → command、JSON decode/validation、可信 Context 构造和 `LogicSystem::PostMeetingCommandWork()`；不直接调用 `MeetingService`，不建立第二 FIFO/worker。
7. 用真实、非阻塞 Wire Collector 替换生产 `CountingNoWireCollector`，把 M6 typed outbound 编码为 JSON 并通过可发送 Session 句柄进入 `CSession` 队列；MeetingService 仍不知道网络层。
8. P3.2 先硬化 Session：每个 `CSession` 一个 Asio strand；所有 socket 操作、写完成、关闭和 transport terminal state 在 strand 内串行；`CServer::_mutex` 与 `UserMgr::_session_mtx` 仅保护各自注册表。
9. 统一 Session Terminal Path：socket 终止、CServer 条件移除、UserMgr 条件移除、SessionDisconnectBridge exactly-once 投递。领域断线仍经唯一 LogicSystem FIFO。
10. `TrySend` 不承诺 L5。同步返回 admission 结果；通过 observer/counters 区分 L2 入队、L3 write success、L4 write failure。无 ACK、retry、可靠投递或 exactly-once。

### 1.2 关键源码发现

- 当前 parser 用 signed `short` 读取 ID/length，负 length 可绕过 `> MAX_LENGTH` 并在转换为 `size_t` 后形成危险读长（`CSession.cpp:148-180`）。
- `_user_uid` 构造未初始化（`CSession.h:67`；`CSession.cpp:10-19`）。
- `CServer::ClearSession()` 的 find/read 未持 `_mutex`，且按 uid 无条件删除 UserMgr 映射（`CServer.cpp:58-70`）。
- `UserMgr::SetUserSession()` 覆盖旧 Session，而 `RmvUserSession(uid)` 不比较 Session 身份；因此“旧 Session 断开删除同 uid 新 Session”真实存在（`UserMgr.cpp:21-36`）。
- 写失败只 `Close()`，不从 `CServer::_sessions` 移除（`CSession.cpp:251-268`）。
- `AsioIOServicePool` 默认两个 io_context/线程；Logic worker 与 gRPC handler 也会调用 `Send`，socket 发起与 Close 没有共同 strand（`AsioIOServicePool.*`、`LogicSystem.cpp`、`ChatServiceImpl.cpp`）。
- M6 adapter/typed outbound 已存在，但生产 collector 只计数，不发送字节（`CountingNoWireCollector.cpp:14-29`）。
- Qt parser 在一次 `readyRead` 内复用绑定旧 `_buffer` 状态的 `QDataStream`，同时用 `_buffer = _buffer.mid(...)` 替换 buffer；多完整帧场景为 **SOURCE-BASED HYPOTHESIS — NOT YET REPRODUCED**（`tcpmgr.cpp:19-58`）。
- 另发现 legacy Qt add-friend response handler 注册在 request ID `1009`，服务端发送 response ID `1010`；这是既有问题，不属于本轮修改范围。

### 1.3 必须先裁决的兼容性缺口

当前 M6 typed `MeetingResponseMessage` 只含 common result、MeetingView、participants/scope；没有 Phase 1 成功契约所需的 `host_participant`、`participant`、`join_outcome`、`leave_outcome`、`close_outcome`。当前 notification 也只保留 `event_id`、`meeting_id`、correlation request id，没有完整 Event 的 owner/time/state/actor 字段。

**RECOMMENDED — PENDING HUMAN APPROVAL**：在 P3.4 前对 M6 typed outbound 做最小、向后兼容的 presence-field 增补；这是把既有 Phase 1 领域结果完整搬运到 wire 边界，不修改 Meeting 状态机、ResultCode 或 M6 的领域隔离职责。单靠 Wire Collector 不能恢复 adapter 已经丢弃的信息。

## 2. Current Architecture

### 2.1 当前请求链路

```text
Qt TcpMgr
  → 4B header + JSON
  → CSession::AsyncReadHead / AsyncReadBody
  → LogicNode
  → LogicSystem::PostMsgToQue
  → SerializedWorkExecutor（唯一 FIFO / 单消费者）
  → LogicSystem legacy callback
```

Meeting 领域已经通过 M4–M6 接入同一执行器，但 `LogicSystem::PostMeetingCommandWork()` 当前没有生产 TCP 调用者。

### 2.2 当前 Meeting 领域链路

```text
LogicSystem（唯一 SerializedWorkExecutor 所有者）
  → LogicWorkDispatcher（唯一 Meeting 分发器）
  → MeetingService（无锁、非 thread-safe、single-writer）
  → MeetingResponseNotificationAdapter
  → MeetingOutboundMessage（typed value）
  → CountingNoWireCollector（仅计数）
```

`SESSION_DISCONNECTED`、`FINALIZE_CLOSE`、Meeting command 和 legacy message 已共用唯一 FIFO。该边界不得被本阶段推翻。

### 2.3 当前网络生命周期

- `CServer::_sessions` 是按 `session_id` 保存 `shared_ptr<CSession>` 的唯一网络注册表。
- `CServer::FindSessionBySessionId()` 在锁内复制共享句柄，但 `ClearSession()` 的前段仍无锁。
- `UserMgr` 是 `uid → 单 Session`，不是 Meeting 多 Session binding 的依据。
- `SessionDisconnectBridge` 只保证领域断线 work 最多投递一次；它不清网络注册表和 UserMgr。
- `CSession::Send()` 是 `void`；queue full、write failure 没有结构化反馈。

## 3. Phase 1 / Phase 2 Frozen Constraints

以下内容是输入约束，不是 P3.1 待优化项：

1. 六项 API：CREATE / JOIN / LEAVE / CLOSE / QUERY / LIST_PARTICIPANTS。
2. Meeting 状态机 `CREATED / ACTIVE / ENDING / CLOSED` 与所有权限、幂等、Snapshot 语义。
3. `(meeting_id, user_id)` 是逻辑 Participant 唯一身份；Session 与 Participant 解耦。
4. MeetingService 不依赖 CSession、CServer、socket、JSON 或协议号。
5. MeetingService 所有 mutation 由唯一 FIFO、唯一消费者串行调用。
6. CloseMeeting 和 FinalizeClose 是两个独立 queue turn。
7. `request_id` 必需但 adapter 可生成；仅 correlation，不是幂等键。
8. 相同 `request_id` 的两次有效 Create 仍创建两个不同 Meeting。
9. `event_id` 是 Event 自身 ID；不得以 request_id 代替。
10. SessionDisconnected 内部事件可无 request_id，不得伪造客户端 request_id。
11. MeetingOutboundAdapter 的 typed 出站边界保留；MeetingService 不直接发送。
12. SessionDisconnectBridge 继续只携带稳定 SessionId 并投递到唯一 FIFO。
13. 无 ACK、retry、MQ、可靠投递、exactly-once delivery。
14. Notification best-effort；目标消失或发送失败不得回滚领域状态。
15. CLOSED 查询只来自 ClosedMeetingSnapshot。

**冻结契约修改请求：无。** 本文发现的 typed outbound 字段缺口属于 Phase 1 契约的完整搬运，不要求改变冻结业务语义；具体扩展仍需负责人批准。

## 4. Existing TCP Frame Analysis

### 4.1 当前 frame

| 层 | 当前事实 |
| --- | --- |
| Message ID | 2 bytes，服务端用 signed `short`，Qt 用 `quint16` |
| Payload length | 2 bytes，network byte order |
| Payload | JSON text |
| Header total | 4 bytes |
| `MAX_LENGTH` | 2048；同时被误用于 buffer/length/ID 校验 |
| Send queue | 常量 1000，但现代码 `>` 导致最多可到 1001 |

### 4.2 A：保留 4-byte frame

**优点**：legacy IM 字节兼容；Qt/ChatServer 改动局部；无需握手、双 parser 或连接级版本状态；现有 SendNode/Qt QDataStream 可演进。

**缺点**：2-byte length 限制单帧 65,535 bytes；无 magic，非法流无法可靠 resync；version 不在 header 中。

### 4.3 B：新 Frame V2

候选为 magic/version/flags/32-bit length/request sequence 的新 header。

**优点**：扩展能力和 resync 更强，能容纳 flags/compression/大 payload。

**缺点**：必须做协议协商或双端同步切换；legacy IM 与 Meeting 同连接时 parser 复杂；Qt、server、测试、所有消息发送路径同时修改；对当前校招 MVP 没有真实需求。

### 4.4 推荐

**RECOMMENDED — PENDING HUMAN APPROVAL**：选择 A。Protocol V2 的“V2”体现在严格类型/校验、ID registry 和 Meeting JSON contract，而不是扩大 header。

兼容策略：

- legacy 合法 IM frame 字节不变；
- Meeting V2 通过新的 message IDs 选择 V2 JSON schema；
- 不增加 header version；`protocol_version: 2` 在 Meeting JSON envelope 中校验；
- 没有 magic 的前提下，任何非法 ID/length 统一终止 Session，不尝试字节流 resync。

### 4.5 四个必须分开的概念

| 概念 | 推荐定义 |
| --- | --- |
| Message ID 合法性 | 必须命中共享 registry 的显式集合；不是 `id <= 2048` |
| Payload length 合法性 | `1..65535`，并满足该 message schema；在分配/读取前验证 |
| 接收缓冲容量 | 实现细节；4B header buffer + 校验后有界 payload buffer，可分块读 |
| 单帧最大长度 | header 4 + payload 65,535 = 65,539 bytes |

`MAX_LENGTH=2048` 只描述当前实现，不进入永久协议规范。

## 5. Protocol V2 Design

### 5.1 Frame contract

```text
offset  size  type             meaning
0       2     uint16, BE       message_id
2       2     uint16, BE       payload_length
4       N     UTF-8 JSON       exactly payload_length bytes
```

- 使用公开/标准端序 API，不继续依赖 `boost::asio::detail::socket_ops`。
- header decode 先复制到 `std::uint16_t`，再做 network-to-host。
- `payload_length == 0` 对当前 JSON 消息非法。
- 校验成功前不得构造 payload node、不得分配 payload、不得开始 body read。
- JSON 必须是 object，UTF-8，有效 `protocol_version == 2`。
- 编码后超过 65,535 bytes：不截断、不拆成多个应用帧；记录 `ENCODE_TOO_LARGE`，该出站消息 best-effort 失败。

### 5.2 Parser safety pipeline

```text
read exactly 4 bytes
  → decode uint16_t id / uint16_t length
  → IsRegisteredMessageId(id)
  → 1 <= length <= kMaxFramePayloadBytes
  → allocate/resize exact bounded payload
  → read exactly length bytes
  → JSON parse / schema validation
  → dispatch
```

非法 header 的统一 terminal reason：`PROTOCOL_INVALID_MESSAGE_ID` 或 `PROTOCOL_INVALID_LENGTH`。因为 frame 无 magic，继续读会让边界可信性下降，所以统一进入 Session Terminal Path。

合法 ID 但 JSON/schema 非法时，frame 边界仍可信：Meeting request 可返回同一 response schema 的 `INVALID_ARGUMENT`，随后继续收帧；legacy handler 行为可保持兼容。若错误响应自身无法编码/入队，仅记录，不重试。

### 5.3 最小改造边界

- `MsgNode` 的长度与 ID 字段改为 unsigned fixed-width；内部 buffer length 使用 `std::size_t`。
- `CSession` 将 header buffer 与 payload buffer分离；删除“用 MAX_LENGTH 判断 message ID”的耦合。
- `SendNode` 编码前验证 ID 与 payload size，禁止 `size_t → short` 静默窄化。
- 不引入新的 transport server、协议握手或 framing library。

### 6.3 三个方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A 两端分别定义 | 零工程改动 | 已出现名称漂移和 handler ID 错配；新增易冲突 | 不推荐 |

## 7. JSON Request/Response/Notification Contracts

### 7.1 编码规则

- JSON field name 使用 snake_case。
- enum 使用冻结名称字符串；数值 ResultCode 同时保留 `code` 与 `name`。
- `UserId` 用 JSON integer；ID 用 UTF-8 string。
- Timestamp 用 UTC RFC 3339，毫秒精度，例如 `2026-11-04T09:00:00.123Z`。
- optional 字段不存在时省略，不用空字符串伪装 presence。
- 未知字段可忽略以支持向后兼容；必需字段缺失/类型错误为 `INVALID_ARGUMENT`。
- 客户端提供任何禁止身份字段时拒绝，不是“忽略后继续”。

### 7.2 Request Envelope

Message ID 已决定 command，JSON 不再重复可冲突的 command 字段：

```json
{
  "protocol_version": 2,
  "request_id": "c9730cb6-b555-4c4e-820b-3384e69e37e5",
  "payload": {
    "meeting_id": "meeting-..."
  }
}
```

- `request_id` 可选；缺失/空值由服务端生成。
- CREATE 的 `payload` 必须是空 object，或可整体省略；客户端不得指定 `meeting_id`。
- JOIN/LEAVE/CLOSE/QUERY/LIST_PARTICIPANTS 只有一个业务字段 `meeting_id`，必需、string、非空；领域只冻结“非空”，wire 层不发明 UUID regex。

禁止客户端字段（任意层级）：

```text
authenticated_user_id / user_id（作为调用身份）
session_id
host_user_id
trusted_owner_chat_server_id
handling_chat_server_id
owner_chat_server_id（作为可信 routing context）
device_id（当前无可信来源）
```

### 7.3 Response Envelope

```json
{
  "protocol_version": 2,
  "message_kind": "response",
  "command": "JOIN",
  "request_id": "...",
  "result": {
    "code": 0,
    "name": "OK",
    "disposition": "SUCCESS"
  },
  "data": {
    "join_outcome": "NEW_PARTICIPANT",
    "meeting": {},
    "participant": {}
  }
}
```

各命令成功/幂等 data：

| Command | data |
| --- | --- |
| CREATE | `meeting`, `host_participant` |
| JOIN | `meeting`, `participant`, `join_outcome` |
| LEAVE | 授权/领域实际提供时 `meeting`；本次成功时 `leave_outcome=LEFT` |
| CLOSE | `meeting`；首次成功时 `close_outcome=CLOSE_STARTED` |
| QUERY | `meeting` |
| LIST_PARTICIPANTS | `meeting`, `participant_view_scope`, `participants` |

Error Result：

```json
{
  "protocol_version": 2,
  "message_kind": "response",
  "command": "CLOSE",
  "request_id": "...",
  "result": {
    "code": 1100,
    "name": "PERMISSION_DENIED",
    "disposition": "ERROR",
    "diagnostic_message": "optional; non-contractual"
  }
}
```

**RECOMMENDED — PENDING HUMAN APPROVAL**：错误 envelope 不增加独立 `meeting_id`；只有 `MEETING_NOT_LOCAL` 可在 result 中携带可信 `owner_chat_server_id`。这与当前 M6 typed contract 一致，且避免在未授权错误中增加资源信息。

### 7.4 MeetingView

```json
{
  "meeting_id": "meeting-...",
  "owner_chat_server_id": "chatserver-1",
  "host_user_id": 42,
  "meeting_state": "ACTIVE",
  "active_participant_count": 3,
  "created_at": "2026-11-04T09:00:00.123Z",
  "closed_at": "2026-11-04T09:30:00.456Z"
}
```

`closed_at` 仅 CLOSED 存在；CLOSED 数据只能来自 ClosedMeetingSnapshot。ERROR 时不因“响应完整”而补 MeetingView。

### 7.5 ParticipantView

```json
{
  "user_id": 42,
  "role": "HOST",
  "participant_state": "ACTIVE",
  "joined_at": "2026-11-04T09:00:00.123Z",
  "left_at": "2026-11-04T09:20:00.000Z"
}
```

`left_at` 仅 LEFT 存在；不暴露 Session、Binding、device、socket 或 presence。

### 7.6 Event / Notification Envelope

完整 Event contract：

```json
{
  "event_id": "event-...",
  "event_type": "MEETING_CLOSED",
  "meeting_id": "meeting-...",
  "owner_chat_server_id": "chatserver-1",
  "occurred_at": "2026-11-04T09:30:00.456Z",
  "meeting_state_after": "CLOSED",
  "actor_user_id": 42,
  "participant_user_id": 7,
  "request_id": "originating-close-request-id"
}
```

presence 规则继承 Phase 1：内部断线产生的 ParticipantLeft 可无 actor/request_id；不得伪造。Notification：

```json
{
  "protocol_version": 2,
  "message_kind": "notification",
  "event": { "event_id": "...", "event_type": "MEETING_CLOSED" }
}
```

当前 M6 仅为 `MEETING_CLOSED` 生成客户端 notification。其余三类是完整 Event wire schema 的保留表达，不等于 P3.4 已承诺广播它们。

### 7.7 typed outbound 字段完整性

**RECOMMENDED — PENDING HUMAN APPROVAL**：P3.4 在不改 MeetingService 的前提下扩展 `MeetingResponseMessage` 的 optional typed fields：host participant、participant、join/leave/close outcome；Notification 保留完整 `MeetingEvent`（或等价字段）。Adapter 继续负责安全 presence 判定，Wire Collector 只序列化 typed value，禁止反查领域或自行推断。

## 8. Request Correlation Design

### 8.1 最小方案

- Qt 对每个 Meeting request 生成新的 UUID string，并用 `QHash<QString, PendingRequest>` 保存 command、发起时间和 UI callback。
- 服务端接受可选 request_id；有效规则建议为 UTF-8 string、1–128 bytes。缺失/空值生成 `req-<uuid>`。
- Response 必须回显最终进入 `MeetingRequestContext` 的 request_id。
- Qt 收到 response 后按 request_id 查 pending；再校验 response `command` 与 pending command 一致，然后完成并移除。
- 未知/已过期 request_id：记录并忽略，不把它当 notification。

### 8.2 语义边界

- request_id 不是 sequence number、事务 ID、幂等键或防重放 token。
- 两次相同 request_id 的 Create 都进入 FIFO并各自创建。
- event_id 始终独立；Notification 的 Event 可带 originating request_id 用于 UI 关联，但去重候选是 event_id。
- SessionDisconnected 无外部 request_id；相关 Event 的 request_id absent。
- 不另建第二个 `wire_correlation_id`：当前 Qt 并发关联用 request_id 已足够。独立 wire sequence 会增加两套关联概念而没有需求。

**RECOMMENDED — PENDING HUMAN APPROVAL**：采用 request_id 直接作为 wire correlation；不增加 transport sequence ID。

## 9. Meeting Command Ingress Architecture

### 9.1 目标链路

```text
Qt Client
  ↓ 4B frame
CSession strand / framed read
  ↓ 已验证 message_id + bounded payload
MeetingCommandIngressAdapter
  ↓ JSON decode + schema validation
  ↓ trusted Session snapshot + local ServerId + request_id
MeetingRequestContextBuilder
  ↓
LogicSystem::PostMeetingCommandWork
  ↓ 唯一 SerializedWorkExecutor FIFO
LogicWorkDispatcher
  ↓
MeetingService
```

### 9.2 组件职责

`MeetingCommandIngressAdapter`：

1. 将 2001–2006 映射到 `ClientMeetingCommandKind`。
2. 解析/验证 JSON envelope；拒绝 forbidden identity 字段。
3. CREATE 不接收 meeting_id；其余五项验证非空 meeting_id。
4. 从当前 CSession 的线程安全认证快照取得 `authenticated_user_id` 与稳定 `session_id`。
5. 从 LogicSystem/启动配置的不可变 `LocalServerId()` 取得 handling server。
6. 采用客户端 request_id 或生成新 request_id。
7. `has_device_id=false`、`has_trusted_owner_chat_server_id=false`；不信任客户端 owner hint。
8. 调用现有 builder 和 `PostMeetingCommandWork()`。

### 9.3 认证与顺序

P3.2 必须给 CSession 明确初始化的认证快照（`has_authenticated_user=false`, `user_id=0`），并以 mutex 或 release/acquire atomic 保证 worker 写入与 ingress 读取无数据竞争。Meeting 客户端正常流程必须等待 chat-login success response 后再发 Meeting command；在认证完成前到达的 pipelined Meeting request 返回 `AUTH_REQUIRED`，不猜测队列中未来会成功的登录。

领域仍会用 DomainSessionRecord 二次验证 context 身份一致性；网络快照不是绕过领域认证。

### 9.4 错误路径

- 非法 frame：进入 terminal path，不创建业务 response。
- 合法 Meeting ID + JSON/schema error：生成/保留 request_id，以 `MEETING_RESPONSE` 返回 `INVALID_ARGUMENT`；不进入 MeetingService。
- 未认证：可构造 user_id=0 的 context并进入领域，得到冻结的 `AUTH_REQUIRED`；或 ingress 生成等价 typed error。为保持单一错误语义和 Domain Session 顺序，推荐前者。
- FIFO stopping：生成 `INTERNAL_ERROR` best-effort response并计数 `ingress_post_rejected`；不重试。
- request body 超限：frame 层终止；不做部分 JSON 解析。

### 9.5 FIFO 保证

Ingress 不持有 MeetingService，不调用 dispatcher；它唯一可用的业务入口是 `PostMeetingCommandWork`。不新建队列、线程、worker、timer，也不把 Meeting command伪装成 legacy `LogicNode` callback。

## 10. Meeting Egress Architecture

### 10.1 目标链路

```text
MeetingService
  ↓ result/events
LogicWorkDispatcher
  ↓
MeetingResponseNotificationAdapter
  ↓ typed MeetingOutboundMessage
MeetingWireCollector
  ↓ JSON encode + choose 2007/2008
IMeetingWireSessionDirectory
  ↓ fresh liveness lookup
IMeetingWireSession::TrySend
  ↓ CSession strand / send queue
TCP → Qt TcpMgr
```

### 10.2 JSON 与 message ID

- JSON 序列化只在 `MeetingWireCollector`（或其纯 encoder helper）发生。
- RESPONSE → 2007；NOTIFICATION → 2008。
- `MeetingResponseNotificationAdapter` 继续只做领域 result → typed message，禁止 JSON/CSession 依赖。
- `MeetingWireEncoder` 建议是纯函数，便于 snapshot/unit test。

### 10.3 Session lookup

M6 adapter 当前先按 SessionId 做判活。真实 wire 发送仍必须做**第二次、即时的 send-capable lookup**，因为 adapter lookup 后 Session 可并发终止。

建议新增独立接口（不把发送方法塞回纯领域类型）：

```text
IMeetingWireSessionDirectory::FindWireSession(session_id)
  → shared_ptr<IMeetingWireSession> or null
IMeetingWireSession::TrySend(encoded_frame, observer)
```

`CServer` 从唯一 `_sessions` registry 在锁内复制句柄；仅 transport state 为 OPEN 的 Session 可返回。不存在或已 TERMINATION_REQUESTED/CLOSED：计 `target_missing_or_closed`，跳过。

### 10.4 Queue full / write failure

- queue full：`TrySend` 返回 `REJECTED_QUEUE_FULL`；collector 计数，不阻塞、不重试、不回滚。
- Session closing：`REJECTED_TERMINATING`。
- encoder failure/oversize：`ENCODE_FAILED`/`ENCODE_TOO_LARGE`。
- async write failure：observer 收到 L4，触发统一 terminal path；不回调 MeetingService。
- write success：只代表 L3，不代表客户端解析/展示。

### 10.5 Notification 多目标

M6 已将 N 个目标展开为 N 条单目标 typed message。Wire Collector逐条独立处理；一个目标失败不影响其他目标，不批量回滚，不重试，不建立 notification queue。

## 11. Session Lifecycle Architecture

### 11.1 Transport state

建议 CSession 使用显式 transport enum：

```text
OPEN
TERMINATION_REQUESTED
CLOSED
```

它与 Meeting Domain 的 `CONNECTED/AUTHENTICATED/CLOSING/CLOSED` 不同：前者由网络/strand维护，后者只由唯一领域 FIFO维护。

初始化规则：

```text
_user_uid = 0
_has_authenticated_user = false
transport_state = OPEN
terminal_once = false
```

### 11.2 Unified Session Terminal Path

```text
RequestTerminate(reason)
  → atomic OPEN → TERMINATION_REQUESTED（拒绝新 Send）
  → post/dispatch 到本 Session strand
  → cancel/shutdown/close socket once
  → cancel/observe pending send items
  → CServer::RemoveSessionIfMatches(session_id, this)
  → UserMgr::RemoveUserSessionIfMatches(uid, session_id)
  → SessionDisconnectBridge::NotifyDisconnected() once
  → transport_state = CLOSED
```

所有入口——read error、write error、invalid frame、explicit Close、server shutdown——只调用 `RequestTerminate(reason)`。重复调用幂等返回 `ALREADY_TERMINATING/CLOSED`。

为避免锁序死锁：

1. strand 内执行 socket terminal transition；
2. `CServer::_mutex` 临界区只 find/compare/copy/erase，不持锁调用 UserMgr/LogicSystem；
3. `UserMgr::_session_mtx` 单独临界区 compare/erase；
4. SessionDisconnectBridge 在自身锁外投递 FIFO。

### 11.3 CServer registry cleanup

`RemoveSessionIfMatches` 在一个 `_mutex` 临界区完成 find、expected identity 比较、auth snapshot capture 和 erase。禁止当前的无锁 find + 后加锁 erase。写失败与非法 header 同样走此路径，所以不会留下“socket closed 但 registry 仍命中”的 Session。

### 11.4 UserMgr conditional cleanup

真实竞态：

```text
uid U → old Session A
uid U 重新登录 → map 覆盖为 Session B
Session A 断开 → RmvUserSession(U) 无条件 erase
结果：Session B 映射被错误删除
```

建议接口按 `(uid, expected_session_id)` 或 expected shared_ptr 比较；只有 map 当前仍指向终止 Session 才 erase。UserMgr 仍是 legacy 单 Session map，Meeting 多 Session 关系继续由领域 Binding 管理。

### 11.5 Exactly-once 边界

- network registry cleanup：compare-and-erase 幂等；
- UserMgr cleanup：conditional erase 幂等；
- domain disconnect dispatch：SessionDisconnectBridge 的 `posted_` 保证最多一次；
- 网络 exactly-once 不等于消息投递 exactly-once；后者仍不承诺。

## 12. Concurrency and Synchronization Design

### 12.1 Asio 模型验证

`AsioIOServicePool` 默认创建两个 io_context，每个由一个线程 run；单个 Session 当前绑定一个 pool io_context，因此它的 socket completion 通常落在该 context 的线程上。但是 Send 的发起者还包括 Logic worker 与 gRPC 线程，Close 也可能从不同线程调用；“一个 io_context 一个 thread”不能自动串行化跨线程发起操作。

### 12.2 方案比较

#### A. mutex 最小同步

优点：改动小；现有 `_send_lock/_session_mtx` 可复用。

缺点：难以覆盖“发起 async operation + completion + close”的 Asio executor 顺序；锁外 async callback 仍有竞态；锁序和重入复杂。

#### B. 每 Session 一个 strand

优点：与 Asio 模型一致；socket 发起、completion、close、send-queue state 都有单一顺序；不同 Session 可并行；无需把业务 FIFO当网络锁。

缺点：外部线程调用 TrySend 后实际 strand 入队存在时间差；需要明确 admission 与 L2 的区别。

#### C. 所有 Session 单线程网络 executor

优点：简单串行。

缺点：全连接共享瓶颈，改变 pool 架构，属于不必要重构。

**RECOMMENDED — PENDING HUMAN APPROVAL**：选择 B。

### 12.3 四种同步机制不混用

| 机制 | 保护对象 | 不负责什么 |
| --- | --- | --- |
| LogicSystem FIFO | Meeting Domain mutation、Domain Session state、work 顺序 | socket、send queue、CServer map |
| per-CSession strand | socket operation、transport state、send queue/completion/Close | Meeting 状态 |
| `CServer::_mutex` | `_sessions` registry | socket 与 UserMgr |
| `UserMgr::_session_mtx` | uid → current legacy Session map | Meeting Binding、CServer map |

### 12.4 strand 与 queue admission

不能把“成功 post 到 strand”谎称为 L2。建议 `TrySend`：

- 用 atomic reserved-slot 计数在调用线程进行非阻塞 bounded admission；满时立即拒绝；
- 成功只返回 `ACCEPTED_FOR_STRAND`；
- strand 真正 push send queue 时发出 `ENQUEUED`（L2）；
- write completion 发出 L3/L4；
- terminal path 释放所有 reservation并为未写 items 发 `CANCELLED`。

队列 hard limit 推荐精确为 1000（in-flight + queued reservations），判据 `>=`，修复当前 1001 偏差。

## 13. Observability Design

### 13.1 Send API

建议具名结果：

```text
SendAdmissionResult:
  ACCEPTED_FOR_STRAND
  REJECTED_QUEUE_FULL
  REJECTED_TERMINATING
  REJECTED_INVALID_FRAME

SendProgressEvent:
  ENQUEUED              // L2
  WRITE_SUCCEEDED       // L3
  WRITE_FAILED          // L4
  CANCELLED_ON_CLOSE    // L4-class terminal outcome
```

`TrySend` 必须快速、非阻塞；completion observer 不回写领域状态。

### 13.2 L2–L5

| Level | 定义 | 可观测方式 | 保证 |
| --- | --- | --- | --- |
| L2 | 进入 Session send queue | strand event + counter | admission accepted 不等于 L2 |
| L3 | async_write 成功完成 | completion counter/structured log | 只表示本机写成功 |
| L4 | async_write 失败可识别 | error_code/reason/counter + terminal reason | 不重试 |
| L5 | 客户端实际收到并处理 | 仅 Qt handler/E2E 测试证据 | 生产协议不增加 ACK，因此不保证 |

### 13.3 指标/日志

最小 counters：

- `frame_invalid_message_id`, `frame_invalid_payload_length`, `json_decode_failed`, `schema_validation_failed`；
- `meeting_ingress_posted`, `meeting_ingress_post_rejected`；
- `wire_encode_succeeded`, `wire_encode_failed`, `wire_encode_too_large`；
- `wire_target_missing`, `wire_target_closed`；
- `send_admission_accepted`, `send_rejected_queue_full`, `send_rejected_terminating`；
- `send_l2_enqueued`, `send_l3_succeeded`, `send_l4_failed`, `send_cancelled`；
- `session_terminal_by_reason`, `session_registry_removed`, `user_mapping_removed/mismatch`。

结构化日志字段按可得性包含：session_id、message_id、command、request_id、event_id、meeting_id、terminal_reason、error_code。禁止记录 token、密码和整段敏感 JSON。

### 14.2 安全专项

必须覆盖原始 header `0xFFFF`：解码为 65535，不得变成 `-1`；若 length=65535且合法则按上限有界分配/读取，若策略最终批准更小上限则在分配前拒绝。ID 65535 不在 registry，必须终止。

### 14.3 顺序专项

- REGISTER 在第一条业务 work 前；AUTHENTICATE 与 Meeting command 按真实 FIFO 顺序。
- CREATE 相同 request_id 两次产生不同 meeting_id。
- first Close response 是 ENDING；之后 notification event 是 CLOSED且有独立 event_id。
- SessionDisconnect Event 无伪 request_id。
- response ordering 与 command FIFO ordering一致；socket write ordering由每 Session strand保证。

本轮按授权没有构建、没有执行 CTest、没有启动 ChatServer/Qt、没有连接 Redis，也没有运行上述未来测试。Qt 多帧问题仍是待 P3.5 复现的源码假设。

## 16. Architecture Decision Records

以下每项都是建议，不是已冻结决定。

### ADR-01 — 保留 4-byte frame

- **当前技术事实**：两端已硬编码 2B ID + 2B length + JSON；legacy IM 全部使用。
- **可选方案**：A 保留；B magic/version/32-bit length 新 header。
- **优缺点**：A 兼容、改动小但扩展有限；B 扩展强但需双 parser/协商和全链迁移。
- **推荐方案**：A，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **理由**：当前需求不需压缩、分片或超 64KiB；展示项目应优先正确性和最小改动。
- **影响**：Meeting V2 通过 ID+JSON schema 版本化。
- **测试**：legacy frame golden、Meeting frame golden、混合粘包/拆包。
- **需负责人裁决**：是。

### ADR-02 — unsigned parser 与单帧 65,535-byte payload 上限

- **事实**：signed short 负值绕过；2048混合了多个概念。
- **方案**：A 继续 short/2048；B uint16 + 2048；C uint16 + wire 上限65535和动态有界 payload。
- **优缺点**：A 不安全；B 安全但把偶然实现固化；C 稍多改动、扩展足够。
- **推荐**：C，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：重构 CSession/MsgNode buffer，但 frame字节兼容。
- **测试**：0、1、2048、2049、65535、原始FFFF、oversize encode。
- **需裁决**：是（payload cap）。

### ADR-03 — Message IDs 2001–2008 + 共享 header

- **事实**：server/Qt duplicate enums；无 Meeting ID；当前编号无内部重复。
- **方案**：A 双定义；B shared header；C generator。
- **优缺点**：B 单一事实源且无新工具；需更新三种工程。
- **推荐**：B与2001–2008，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：P3.2/P3.5 更新 include/project wiring；legacy value 不变。
- **测试**：registry uniqueness、两端 compile/static assertion、golden headers。
- **需裁决**：是。

### ADR-04 — JSON V2 envelope

- **事实**：legacy 已用 JSON；Phase 1 字段语义冻结但无 wire schema。
- **方案**：A JSON；B protobuf；C自定义二进制。
- **优缺点**：JSON 可演示/调试且复用依赖；体积较大但 64KiB 对 MVP足够。
- **推荐**：A，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：新增纯 encoder/decoder；不修改 `message.proto`。
- **测试**：schema matrix、unknown/forbidden fields、timestamp、round-trip。
- **需裁决**：是。

### ADR-05 — request_id 直接承担 wire correlation

- **事实**：领域 request_id 必需且可由 adapter生成；不是幂等键。
- **方案**：A optional client request_id+server fallback；B另增 wire sequence；C服务端永远生成。
- **优缺点**：A 可支持 Qt 并发且概念最少；B 两套 ID复杂；C 客户端发出时无法预登记 correlation。
- **推荐**：A，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：Qt pending map；服务端 UUID fallback；重复不去重。
- **测试**：并发乱序 response、duplicate request_id Create、missing fallback。
- **需裁决**：是。

### ADR-06 — 独立 Ingress Adapter、唯一 FIFO

- **事实**：PostMeetingCommandWork 无生产 caller；MeetingService非线程安全。
- **方案**：A network callback直调 service；B legacy callback内解析；C独立 adapter后投现有 typed work。
- **优缺点**：C 边界清晰、可单测、不建第二队列；增加小组件。
- **推荐**：C，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：CSession路由 2001–2006到 adapter；LogicSystem API不变。
- **测试**：context trust、ID映射、FIFO ordering、post rejection。
- **需裁决**：否（由冻结架构强制），组件命名/文件落点可在实施评审。

### ADR-07 — Wire Collector 与 typed outbound 最小扩展

- **事实**：CountingNoWireCollector不发送；现 typed object缺 Phase 1 部分结果/Event字段。
- **方案**：A collector反查/推断；B最小扩展typed value后纯编码；C绕过M6从service直接发。
- **优缺点**：B 保留职责且字段不丢；需改M6 typed/adapter测试。A/C破坏边界或不可能恢复信息。
- **推荐**：B，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：不改领域；P3.4扩展 presence fields并替换生产 collector。
- **测试**：六response逐字段、Event完整性、安全视图、missing target。
- **需裁决**：是。

### ADR-08 — 每 Session 一个 Asio strand

- **事实**：Send来自worker/gRPC，completion在pool，Close可并发；mutex未覆盖executor顺序。
- **方案**：A mutex；B strand；C全局单网络线程。
- **优缺点**：B 精确串行socket且Session间并行；需要异步admission语义。A易竞态；C过度重构。
- **推荐**：B，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：所有read/write/close initiation和completion绑定同strand。
- **测试**：并发Send/Close、write failure、无双写/双close。
- **需裁决**：是。

### ADR-09 — Unified Session Terminal Path + conditional cleanup

- **事实**：写失败不清registry；ClearSession无锁；UserMgr可误删新Session；Bridge不清网络表。
- **方案**：A每错误点补代码；B统一幂等terminal coordinator。
- **优缺点**：B 可证明、可测试；需要收敛旧入口。A继续遗漏/重复。
- **推荐**：B，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：所有终止入口只调用RequestTerminate；registry/UserMgr compare-and-erase。
- **测试**：未登录终止、重复终止、A/B替换、registry race、Bridge一次。
- **需裁决**：是。

### ADR-10 — 非阻塞 Send admission + L2–L4 observer

- **事实**：Send void；queue full静默；strand post与实际入队有时间差。
- **方案**：A继续void；B同步阻塞等strand；C非阻塞admission+async progress。
- **优缺点**：C 不阻塞logic worker并准确区分层级；接口比bool稍多。B可能死锁/阻塞。
- **推荐**：C，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：queue hard limit 1000；collector/observer counters。
- **测试**：full、closing、L2/L3/L4、cancel释放reservation。
- **需裁决**：是。

### ADR-11 — 不增加 ACK/retry

- **事实**：Phase 1 已冻结无ACK/retry/exactly-once。
- **方案**：A继承；B新增可靠投递。
- **优缺点**：A符合范围；L5不可生产确认。B直接修改冻结契约并显著复杂化。
- **推荐**：A，**RECOMMENDED — PENDING HUMAN APPROVAL**（实质上是继承冻结约束）。
- **影响**：P3.6只能以测试证据声明L5；运行时不承诺。
- **测试**：客户端handler E2E；无retry断言。
- **需裁决**：否，除非负责人明确启动Phase 1契约变更。

### ADR-12 — 错误响应不新增独立 meeting_id

- **事实**：当前 M6 response没有独立 meeting_id；错误视图受安全边界保护。
- **方案**：A不增加；B所有错误回显请求meeting_id。
- **优缺点**：A最小且避免泄露；B便于UI但需typed contract扩展和安全矩阵。
- **推荐**：A，**RECOMMENDED — PENDING HUMAN APPROVAL**。
- **影响**：Qt用 request_id定位请求；MEETING_NOT_LOCAL仅回可信owner。
- **测试**：错误response无view/meeting_id；correlation仍可用。
- **需裁决**：是。
